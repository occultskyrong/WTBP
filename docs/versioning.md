# 版本与版本线治理

## 两个概念

- **版本号**：根目录 `VERSION` 中的 `MAJOR.MINOR.PATCH`，代表当前分支携带的 WTBP 对外认知变化。
- **版本线**：一串存在祖先关系的提交。只有同一条版本线中的版本才可以比较“下一版”；不能把另一条未合并任务分支的版本号当作当前分支的基线。

`master` 是已合并主线；版本变更合入后，仓库检查通过才会创建不可变 `vX.Y.Z` Tag，只有 Tag 才表示正式发布。任务分支可先产生待合并版本记录，但它们不是已发布版本，也不会自动改变 `master` 或其他独立任务分支的基线。

## 本次问题与处理

当前 Figma 任务从 `master@0.5.2` 创建并写入 `0.5.3`。后来刷新远端引用后确认，
`feat/260817_knowledge-curation` 已通过 PR #18 合并，`master` 已推进到 `0.7.1` 并发布
`v0.7.1`。根因是此前本地 `origin/master` 引用过期，导致“当前主线版本”和“任务创建时的祖先版本”被混为一谈。

正确处理不是把 `0.7.1` 直接抄到另一条独立分支，而是：

1. 任务创建时，以当时最新 `master` 的连续版本为准，例如 `0.5.2 → 0.5.3`；这不代表该任务可在主线已推进后直接合并。
2. 若主线已推进，先保存当前任务提交，再合并或从最新 `master` 重建任务分支；保留独立规范变更时，下一次版本必须从新的主线版本递增，例如 `0.7.1 → 0.7.2`。不得把 `0.7.1` 复制到任务分支来伪造基线。
3. 每次版本变动都同时更新 [`CHANGELOG.md`](../CHANGELOG.md)，区分“当前任务分支”“已合并主线”和“未合并任务线”。

## 三段式规则

| 级别 | 适用情况 | 版本动作 |
|---|---|---|
| MAJOR | 不兼容的治理、字段、目录或 Skill 输出契约变化 | 主版本加一，MINOR/PATCH 归零，并记录迁移与破坏性影响。 |
| MINOR | 新增 Practice、Skill、Eval、外部能力卡或对外可发现能力 | 次版本加一，PATCH 归零。 |
| PATCH | 向后兼容的修复、规则补强或已有能力改进 | PATCH 加一。 |
| 不变 | 排版、错别字、注释、链接文字等不改变规范或可发现内容的改动 | 不修改 `VERSION` 或版本日志条目。 |

一次变更只选择最高级别。版本必须在其父提交/合并基线之上严格递增一级；禁止回退、跳跃或借用无祖先关系分支的版本号。

## 提交门禁

`make commit-checklist` 会在版本检查阶段执行：

1. 验证 `VERSION` 的三段式格式及与基线的合法递增。
2. 当 `VERSION` 变动时，要求 `CHANGELOG.md` 同时变动，并包含当前 `### [X.Y.Z]` 条目。
3. 对已经含有版本日志的历史范围，逐提交检查版本与日志是否成对出现。
4. 在版本日志中区分 `master` 主线、待合并任务线和已发布 Tag；任务分支不能凭日志获得发布状态。

这项检查只能验证 Git 可见的祖先关系和已记录的版本线，不能猜测当前任务是否“业务上想依赖”另一条分支。因此创建任务时仍必须先确认正确基线。
