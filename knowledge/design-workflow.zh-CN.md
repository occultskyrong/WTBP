# 共享设计流程与验收契约

这是 WTBP 设计类 Skill 的共享流程。创建、演进、实现或验收视觉产物前，先阅读[上游设计原则与分层框架](design-principles.zh-CN.md)，再阅读本操作契约。流程采用失败即停止：用户提示词、`start` 或要求跳过问题，都不能替代缺失的简报、未解决的实质冲突、清单审批或产物证据。

## 1. 范围与结果

设计工作按顺序产生两个不同结果：

1. 供用户审批的、基于证据的概览和变更清单；
2. 通过必要门禁后，才产生带注释的视觉产物，或实现/验收结果。

除非目标 Skill 明确负责，不得实现产品代码、修改运行配置、估算交付，也不得把视觉方案称为已实现契约。设计清单保持在功能层，不扩写成 API、数据库、类或工程任务拆分。

## 2. 最小简报与终端

视觉变更前必须确认：

- 目标结果；
- 角色与目标终端；
- 产品与平台；
- 入口和主流程；
- 范围内与排除范围；
- 是否确实要求视觉产物。

终端和角色必须使用目标产品或项目自身定义的标签。如果需要使用共享分类，必须先在认知记录中写明映射；不得从其他项目、示例或仓库名称引入角色。根据路由、认证、权限、调用方和产品文案判断所有权；不得因为页面是移动端就推断终端。

组合页面前，必须依据目标终端和证据定义终端外框契约：外框类型、视口/Frame 尺寸、设备外壳、安全区、导航栏、状态区以及嵌入式浏览器或宿主约束。每个 Figma 产品页面都必须用可见的终端外框或视口边界包围完整页面，不得交付裸画布。不得凭空添加通用手机外框；`miniapp` 必须明确展示适用的小程序视口及设备/状态栏/导航栏/TabBar 外框；`app-ios` 或 `app-android` 必须展示声明的设备和安全区外壳；`web` 必须展示批准的浏览器外框，或有名称且边界可见的浏览器/视口容器。只有浏览器外壳不属于产品契约时才能省略浏览器 Chrome，但视口容器和页面范围仍必须可见。来源和尺寸必须写入清单与验收矩阵。

设计存在重叠时，还必须确认源设计时间和用户选定的权威基线。任一缺失时标记为 `Unverified`，停止合并，直到冲突可以解决。

## 3. 需求与证据门禁

用户提供需求文档、文件、链接或完整需求内容时，设计前建立简短认知记录：

- 来源、标题、版本/日期和权威性；
- 结果、角色、终端、产品、入口和旅程；
- 范围内和排除能力；
- 业务规则、权限、状态、操作/转移、恢复路径、例外、验收条件和开放问题。

对文档内部、当前证据和已批准历史执行冲突检查。影响结果、角色/终端、旅程、范围、权限/数据范围、权威规则、破坏性后果、页面结构或可用状态的冲突属于实质冲突。说明双方，提供 2–3 个不同解决方案及取舍；只有证据支持时才推荐；用户选择前停止。

证据优先级为：已批准用户决策、权威需求文档、当前归属 API/字典/权限契约、已核验当前 UI、实现推断。每条重要规则或值记录简短定位：来源类型和章节、仓库/分支/提交及文件/符号、API/字典键，或决策及日期。证据不可访问或已过期时使用 `Unverified / 待确认`，不得猜成“已有”或“新增”。

## 4. 项目设计契约门禁

在设计整体信息架构或修改 Figma/HTML 前，只要存在实际消费项目，就必须先检查该项目。使用仓库/运行时证据，不能只依赖截图或提示词，并创建版本化契约 `PDC-YYYYMMDD-VNN`。如果确实是全新项目或 `figma-only` 项目，没有消费仓库，必须明确记录这个边界，并把依赖实现的字段标记为 `Unverified`，不能自行补全。

契约必须记录：

1. **项目身份与目标（`PDC-01`）**：仓库/工作树、分支/提交或 Figma 基线、产品、平台、声明终端、运行/预览入口和检查日期。
2. **表面清单（`PDC-02`）**：已有路由/入口、页面族、状态、导航外壳、viewport/设备目标，以及每个表面的归属功能或模块。
3. **设计基础（`PDC-03`）**：可复用组件/Variants、Tokens/Variables、字体、资源、图标、布局约定及其来源路径或 Figma 节点 ID。图标复用前必须记录已有图标库/来源、语义命名、支持的尺寸/风格/状态、归属/许可证，以及未知或冲突的家族规则。
4. **行为与约束（`PDC-04`）**：权限、数据/API 边界、操作/转移、响应式规则、可访问性要求、外框/安全区限制和已知平台限制。
5. **复用与变更边界（`PDC-05`）**：哪些是 `Existing — reuse`、`Existing — modify`、`New`、`Conflict` 或 `Unverified`；必须复用和允许扩展的部分、消费者影响，以及禁止重建或修改的部分。
6. **证据与决策（`PDC-06`）**：来源定位、截图/运行捕获、冲突、已批准决策、契约修订号、未解决的 `Unverified` 项和下一位复核人。

填写时可从[项目设计契约模板](templates/project-design-contract-template.zh-CN.md)开始，并为每个字段补充仓库和运行时定位。
模板只是记录工具，不能替代对实际项目的检查。

架构设计前必须执行项目契约冲突检查。路由归属、组件/Token 契约、终端、状态、权限/数据范围或布局约束不一致时都属于阻塞问题。用户批准契约，或明确接受列出的 `Unverified` 边界前，不得设计新的页面族或视觉基础。

项目设计契约是整体架构、变更清单、设计基础、底层窗体批次、实现映射和验收矩阵的来源。契约过期时，必须重新读取并生成新修订，才能继续下游工作。

### 架构推导门禁

项目设计契约获批后，必须先推导整体架构并生成 `ARC-YYYYMMDD-VNN`，再创建或修改变更清单和视觉产物。架构记录必须把契约映射为：

- 业务模块、路由/入口、页面族和导航关系；
- 表面归属、终端外框、viewport/设备尺寸和安全区边界；
- 复用、扩展和确实需要新建的组件/设计基础决策；
- 状态、转移、权限/数据和恢复路径的责任归属；
- 完整页面/状态底层窗体批次及下游实现/验收目标；
- 被否决的方案、重要取舍，以及支持每项决策的 PDC 定位。

如果架构引入了 PDC-01 至 PDC-06 中没有记录的路由、页面族、组件基础、终端、状态或行为，必须先创建新的契约修订并完成冲突决策，否则架构门禁阻断。证据交接可使用[项目设计契约模板](templates/project-design-contract-template.zh-CN.md)，并在变更清单和设计批次中记录 `ARC` 修订号。

## 5. 变更清单审批门禁

创建或修改 Figma/HTML 前，返回 `INV-YYYYMMDD-VNN` 清单版本，日期使用实际清单日期，序号使用当天下一个未使用版本。使用 `F-01` 等稳定功能 ID；只要用户可见结果不变，ID 就保持不变。

每行包含功能名、状态、终端/用户、预计页面、重要状态、入口/操作/转移预期，以及一句话变更。只使用：

- `Existing — reuse`：已核验能力保持不变或组合进旅程；
- `Existing — modify`：已核验能力的行为、范围、文案、状态或呈现发生变化；
- `New`：已检查目标入口/路由、调用方及归属契约/字典/权限面，未找到范围内用户可见结果；
- `Conflict`：与证据、已批准决策、终端权限、平台限制或其他范围项冲突；
- `Unverified`：当前证据无法确认状态。

始终包含可见的冲突/决策区，即使结论是未发现实质冲突。要求用户审批明确的清单版本。审批只覆盖该版本及其行，单独列出的阻塞决策仍未解决。范围、行、冲突解决或阻塞决策变化时创建下一版清单。当前清单获批且所有阻塞决策解决前，不得修改视觉产物。

### 页面规格门禁

清单获批后、抽取页面级公共基础之前、构造底层窗体之前或实现目标代码之前，为每个获批页面/状态建立一份 `PS-YYYYMMDD-VNN` **页面设计与实现规格**。使用[页面规格模板](templates/page-specification-template.zh-CN.md)。页面规格是从项目级 `PDC`/`ARC`/`INV` 记录到具体页面的必经桥梁；它不是一段注释，也不得把说明文字放入产品 UI。

页面规格的阻断门禁如下：

1. **页面说明与边界（`PS-01`）**：记录用户结果、入口、核心任务、退出/恢复、获批功能/页面/状态范围、排除项、未确认事实、证据定位和必须存在的右侧注释。
2. **元素清单与层级（`PS-02`）**：每个可见或可交互元素恰好枚举一次，包含语义角色、父级/区域、内容/数据来源、状态、布局角色、Figma 节点/目标归属和证据。普通元素必须有正常流/Auto Layout 责任层；浮层必须有包含父级、锚点和原因。
3. **基础与组件复用（`PS-03`）**：为每个元素决定 `reuse`、`extend`、`new` 或 `Unverified`，再映射可复用组件/变体、Token/字型/Icon/资产、Code Connect 或项目映射以及允许扩展。页面局部组件克隆、任意 CSS 和视觉相似资产都不能填补缺失映射。
4. **分层计划（`PS-04`）**：同时批准 Figma 与目标实现的 L0 结构底层、L1 公共基础、L2 页面编排/状态、L3 范围内完成顺序。前一层没有必要证明或没有具名获批例外时，不得开始后一层。
5. **设计到代码交接（`PS-05`）**：把每个元素映射到 Figma 和目标组件/文件、布局责任层、视口/状态和验收证据。目标实现必须使用该映射；仅 Figma 页面把目标映射记录为 `Unverified`，不能称代码已完成。

缺少页面说明、元素清单不完整、复用决策未解决、没有分层计划或设计到代码边界未映射时，必须阻断页面特有样式、代码实现和验收。只有页面结果、元素层级、组件映射和分层计划均未变化的窄范围 patch 才能复用当前页面规格；否则必须修订并审批。

### 动作组契约门禁

只有当前清单获批后，才能基于真实项目/Figma 组件证据建立 `AGC-YYYYMMDD-VNN`。使用[动作组契约模板](templates/action-group-contract-template.zh-CN.md)。这是一份可复用交互记录，不是页面级 CSS：将每个获批交互区域分类为 `single-action`、`action-group`、`symmetric-navigation` 或 `segmented-selection`，再映射其语义动作、组件、Token、宽度/槽位策略、状态和验收证据。

动作组的阻断门禁如下：

1. **分类与范围（`AGC-01`）**：每个交互区域映射到获批功能/页面/状态 ID，不得在同一组混入不相关动作。
2. **组件复用（`AGC-02`）**：复用已批准组件/Variant 或记录最小扩展；页面局部按钮克隆、矢量和 CSS 补偿方案不能充当组件契约。
3. **热区与密度（`AGC-03`）**：热区、Icon/文字视觉尺寸、内边距、gap 和任何 full-span 例外必须映射 Token 和终端证据；宽大的描边表面不得把多个小动作伪装为一个按钮。
4. **分布与居中（`AGC-04`）**：用 Auto Layout/Flex/Grid 编码 `content`、`equal`、`full-span` 宽度和 `natural`、`equal-slot`、`equal-partition` 分布。`symmetric-navigation` 必须使用同尺寸边缘热区，中间子项相对父级居中；`space-between` 或手工坐标不能证明其成立。
5. **状态与可访问性（`AGC-05`）**：适用时记录默认、hover、pressed、focus-visible、selected、disabled、loading，以及对比度、键盘行为和纯图标动作的可访问名称。
6. **实现与证据（`AGC-06`）**：将 Figma 组件/Token 映射到目标组件/CSS，并定义验收所需 Figma/DOM 几何、视口/状态、截图和人工复核。

分类缺失、未经批准的 full-span 控件、对称导航边缘槽位不等、热区证据缺失或页面局部补偿规则，都会阻断页面级样式、实现交接和验收。

### 视觉资产与 Icon 门禁

只有当前清单获批后，才能基于真实项目/Figma 证据建立 `ICON-YYYYMMDD-VNN`。使用[图标与视觉资产清单模板](templates/icon-asset-inventory-template.zh-CN.md)。这是一份可复用资产记录，不是页面注释：只抽离清单中批准页面/状态使用的每个 Icon，并映射到可复用组件或已批准来源。

图标资产的阻断门禁如下：

1. **来源与归属（`IA-01`）**：检查项目/Figma 图标库、来源路径/节点、许可证/权限和新鲜度；不得从截图推断归属。
2. **语义抽离（`IA-02`）**：把每个页面 Icon 映射为语义 `ICON-*` ID；页面内临时 Vector、Emoji、文字字形、截图和未批准的第三方图标集都不是可复用 Icon 资产。
3. **尺寸与家族（`IA-03`）**：按终端角色只定义需要的 16/20/24/32 变体，并记录矢量母版、网格/像素对齐、线框/填充规则、描边/端点/连接/圆角规则和光学边界规则。`48px+` 用于插画/空状态作品，而不是常规 UI Icon。直接缩放会破坏光学平衡时，必须独立设计校正变体，不能拉伸同一个源。
4. **状态与 Token 映射（`IA-04`）**：仅在适用时记录默认、选中/激活、禁用、危险、反白和加载变体，以及颜色 Token 和深色/反白行为；不得硬编码颜色。
5. **缺失 Icon 设计（`IA-05`）**：每个缺失 Icon 都必须在进入页面前设计为独立可复用组件。逐个所需尺寸与已批准家族比对，并记录复核决策和组件/节点。
6. **实现映射（`IA-06`）**：每个 Figma 与目标产品实例都映射到相同 Icon ID、组件、尺寸、状态和准确资产/导出物；视觉相似的替代品不能通过。
7. **渲染保真（`IA-07`）**：在声明终端外框中检查所需尺寸/状态的像素对齐、光学平衡、对比度、触达区分离、裁剪和回退行为。

还要记录关联资产是否就绪：字体（许可证/字重/回退/加载）、Logo/品牌标记（批准变体和禁止重绘规则）、图片/插画（来源/版权/裁切/密度）以及关键动效（触发/减弱动效或静态回退）。只有批准范围确实未使用时才标记 `N/A`。

来源缺失、图标家族未批准、视觉资产未确认或页面 Icon 未映射时，必须阻断页面级样式、实现交接和验收。真正全新或 `figma-only` 工作中，必须把缺少项目图标库记录为 `Unverified`；新 Icon 在清单获批前只是可复核候选，不得称为既有资产。

### 外部设计能力门禁

WTBP 负责项目级证据和门禁编排，不重复实现外部设计工具本身。默认使用当前客户端提供的官方 Figma 能力：用 `figma-use` 读取/写入 Figma；仅当已批准的设计基础缺失时使用 `figma-generate-library`；用 `figma-code-connect` 建立可持久的代码/组件映射；用 Figma 的设计上下文/实现能力完成有范围的检查与交接。必须记录哪些能力可用且实际使用；能力不可用时标记为 `Unverified`，不得伪造其结果。

外部能力门禁如下：

1. **官方能力与权限（`EX-01`）**：使用前证明当前客户端提供所需官方 Figma 能力，且用户已授权其声明的 Figma 读取/写入范围。
2. **组件/代码事实来源（`EX-02`）**：优先使用已核验的 Code Connect 或项目组件映射，而不是生成近似实现。缺失映射应作为 PDC/AGC/ICON 决策记录，不能创建页面局部克隆。
3. **可选审计边界（`EX-03`）**：第三方设计 lint、Token 或可访问性审计，只有在用户明确授权、来源/版本已审查、并确认其 Figma 凭据和命令执行要求后才能运行。其结果只能补充，不能替代 AGC、BF、G 或真实夹具验收证据。
4. **禁止隐式安装或凭据读取（`EX-04`）**：不得因为审计可能有帮助就安装第三方 Skill/插件、索取个人访问令牌、读取环境密钥或传输 Figma 节点。应报告缺少的依赖和下一步所需授权。

只有官方默认能力属于正常 Figma 流程。第三方来源在使用方项目明确批准安装和权限前，都只是可选或参考能力；来源和采用方式见面向人类的外部能力登记。

## 6. 产物组织与评审单元

审批后使用实际创建/修订日期分配 `YYYY-MM-DD-VNN` 设计批次，并使用当天下一个未使用序号。组织方式为：

`日期批次 → 业务模块 → 平台子区 → 独立页面/状态 Frame`

每个范围功能都显示在完整容器页面中。页面包含声明的终端外框及其批准尺寸、任务上下文、内容、操作和相关列表/表单/状态结构。弹层要展示完整底层页面。不得交付孤立控件、裁剪组件、共享边缘的大 Frame 或连接线流程。

每个产品 Frame 右侧都要有一个独立评审注释块，作为同级元素。默认几何要求为间距 `48px`、顶部对齐误差不超过 `4px`、注释宽度 `400px`、四周内边距 `24px`、高度随内容增长。注释块可以比页面高或低；不得裁剪、隐藏溢出、强制等高或让换行文字越过边界。产品 Frame 只能包含面向用户的产品 UI；设计解释、项目描述、技术说明、验收规则和评审意见必须放在右侧同级块中，不能写进产品 Frame。

注释按以下顺序组织，可省略确实不适用的区段：`Identity`、`User and outcome`、`Entry and scope`、`Fields and filters`、`Rules and provenance`、`Actions and states`、`Exceptions`、`Copy for review`、`Decision/rationale`、`Acceptance record`。

### 底层窗体优先构建检查点

在添加页面级组件、内容样式、状态装饰或视觉润色前，先确认每个页面/状态都有获批 `PS-YYYYMMDD-VNN`，再为清单中所有批准的页面/状态完成一批**底层窗体**。每个底层窗体只包含来自 L0 的共享结构骨架：声明的终端外框、页面根节点、导航/状态面、安全区行为、内容区域、Auto Layout/正常流父级、必要时命名的浮层父级、状态插槽和右侧独立注释同级块。使用中性占位，不得用装饰样式或最终文案掩盖尚未解决的几何问题。

必须对整批底层窗体执行以下阻断检查点：

1. **页面覆盖（`BF-01`）**：每个批准的页面/状态 ID 都有且只有一个底层 Frame，不得引入未批准 Frame。
2. **外框契约（`BF-02`）**：每个底层 Frame 都使用声明的终端外框、视口/设备尺寸、安全区和导航/状态面，并以可见外边界包围完整页面。通用手机框、裸画布或裁剪页面不能满足另一种已声明终端。
3. **根几何（`BF-03`）**：页面根节点、内容区域和主要间距都有明确尺寸/约束及布局责任层；不得存在无法解释的坐标或溢出。
4. **流式层级（`BF-04`）**：普通区域使用 Auto Layout/正常流；每个有意浮层都有命名父级、锚点和原因。
5. **状态骨架（`BF-05`）**：批准矩阵中的所有重要状态和转移插槽都已表示，不得臆造行为，也不得只润色某一个页面。
6. **评审隔离（`BF-06`）**：每个底层 Frame 已有右侧独立注释同级块，产品 Frame 内没有设计/项目/技术/验收说明。

记录页面规格 ID、底层 Frame ID、外框尺寸、布局责任层证据、中性截图和全部 `BF-01`–`BF-06` 结果。检查点失败、部分完成或未确认时，必须阻断所有上层样式构建。通过后，再分批实现 L1 公共组件、L2 页面编排/状态和 L3 页面级样式；每次写入都必须处于获批 PS-03 复用矩阵和 PS-04 分层计划内。发生结构变化时，重新执行适用的页面、底层和共享门禁。

每次视觉写入批次后，必须对目标产物中的**所有**产品页面/状态 Frame 执行写入后结构门禁，不能只检查本次修改的 Frame。门禁通过或记录已审批例外前，不得继续写入，也不得声称完成：

1. **布局责任层与分布（`G-01`）**：检查并记录每个页面/Frame 的 Figma `layoutMode`（或 DOM 的等价布局责任层）。普通内容必须保持 Auto Layout/正常流。只有明确属于浮层、画布或固定控件容器，且已记录原因时才允许 `NONE`；不得为了对齐把普通子元素改成 absolute。重新执行适用的 `AGC-01`～`AGC-06` 几何检查：等权导航、TabBar、Tabs 或分段控件必须记录分布规则、子项权重/基准宽度、分区中心点和容差；`symmetric-navigation` 还必须记录左右热区等尺寸和中间项到父级中心的容差。评审发现节点迁移、页面增删或 Section 列数变化时，必须依据实际内容边界加已声明的固定内边距，重新计算每个受影响 Section 的边界；不得沿用旧固定宽度或高度。记录触发变更、子元素/列输入、固定内边距和重算几何。手工坐标、把 `space-between` 当作居中证明、过期的固定 Section 尺寸或肉眼可见的不等分都使门禁失败，除非有已批准的产品规则解释。
2. **注释配对（`G-02`）**：枚举每个产品页面/状态 Frame，并证明它与一个独立注释同级块一一对应。注释必须在产品 UI 外、位于右侧、顶部对齐；除非已有审批例外，默认间距为 `48px`。
3. **递归文字与组件边界（`G-03`）**：递归遍历每个产品页面/状态下的所有后代文字节点、组件实例、资源和嵌套容器，包括共享实例内部的后代。字体/资源加载完成后，将每个节点与直接父级比较，并沿祖先链追踪实际溢出。记录节点、父级、祖先和几何；子节点不得越过要求的父级/祖先边界，也不得用裁剪/隐藏溢出来掩盖失败。只检查页面级边界不能通过门禁。
4. **实例与 Master 尺寸比例（`G-04`）**：对每个共享组件实例检查其 Master/组件几何，记录 `实例宽度 / Master 宽度` 和 `实例高度 / Master 高度`。除非有已记录并获批的响应式、Variant 或约束规则，否则比例必须为 `1.0`；无法解释的变形阻断验收。
5. **终端外框与高保真（`G-05`）**：记录目标终端、所选外框类型、尺寸、可见外边界、设备/浏览器外壳、安全区和导航面。截图必须显示完整外框和产品页面；小程序必须显示适用的小程序外框，App Frame 必须展示声明的设备/安全区外壳，Web Frame 必须展示声明的浏览器或边界可见的视口容器。裸画布、通用设备框或任何偏离目标契约的情况都阻断验收。
6. **产品内容隔离（`G-06`）**：检查产品 Frame 中每个可见文字节点。只允许已验证或明确标记的产品文案；设计/项目描述及技术、验收说明必须从产品 Frame 移除，需要保留时放到右侧同级注释块。

门禁记录必须包含产物修订号、检查过的页面/Frame ID、终端外框契约、底层 Frame ID 和 `BF-01`–`BF-06` 结果、`AGC-01`～`AGC-06` 结果、`G-01`–`G-06` 结果、几何来源、截图、例外和复跑结果。节点写入成功、静态检查或单张截图都不能替代这份门禁记录。

## 7. 文案与状态规则

产品 Frame 内的每个文字节点必须归类为：

- 有可追溯需求/UI/契约/决策来源的已核验产品文案；
- 为已批准功能所必需、但在注释中标记 `Copy for review / 待确认文案` 的建议产品文案；
- 移到产品 Frame 外的设计说明；
- 删除的不受支持文案。

页面、项目、实现或验收的描述都不是产品文案，只能放在右侧独立注释块中；产品 Frame 含有这些说明时，`G-06` 失败。

当可用操作、权限/数据范围、主要内容结构、完成结果或恢复路径发生实质变化时，创建独立状态 Frame，例如适用的空态、已填充、加载、禁用、成功、校验失败、错误和无权限态。不要制造无关状态。

## 8. 验收证据

实际产物的验收必须同时具备结构、渲染和来源证据：

1. 枚举所有产品页面/状态 Frame，并检查 Figma 节点几何或 HTML DOM 边界；
2. 确认 `BF-01`–`BF-06` 底层窗体检查点已通过，再评估上层样式；
3. 对每个页面/Frame 执行并记录 `G-01`：`layoutMode` 或等价布局责任层；
4. 执行并记录 `G-02`：页面与独立右侧注释一一配对、顶部对齐和默认 `48px` 间距；
5. 执行并记录 `G-03`：字体/资源加载完成后递归遍历所有后代文字/组件/容器，检查直接父级和祖先边界；只检查页面级溢出不算通过；
6. 执行并记录 `G-04`：每个共享组件实例与 Master 的宽高比例及获批例外；
7. 执行并记录 `G-05`：目标终端外框、准确尺寸、设备/浏览器外壳、安全区和完整外框截图；
8. 执行并记录 `G-06`：产品内容隔离，以及产品 Frame 中不存在描述性/技术/评审文字；
9. 对每个获批交互组执行并记录 `AGC-01`～`AGC-06`，包括热区几何和声明的槽位/分区行为；
10. 对批准范围使用的每个 Icon 和关联视觉资产执行并记录 `IA-01`–`IA-07`；
11. 确认完整页面上下文和正确平台壳层；
12. 核对字段、筛选、枚举、权限、操作、状态转移、恢复路径、排序/分页、例外和来源；未知值标为 `Unverified`；
13. 记录页面内每个文字分类，并为建议文案建立对应复核项；
14. 按明确比例截取渲染截图，检查重叠、裁剪、碰撞、层级、状态和主要操作；
15. 适用时检查可访问性证据：普通文字对比度至少 `4.5:1`，大文字和关键非文字 UI 至少 `3:1`，状态不能只靠颜色表达，HTML 要有可见焦点和键盘顺序；
16. 对照已批准的页面/状态/转移矩阵检查原型连线或运行时操作转移；
17. 每次视觉修复后重新运行完整审计。

提示词回复、生成代码、节点创建成功、静态检查、单张看似合理的截图或 Skill-Up dry-run 都不是产物验收证据。要证明实现/视觉用例解决，必须保留 Figma/预览链接、target、viewport/设备、状态、确定性数据/截图条件、失败基线、预期参考、修复后截图、首个责任布局层、变更文件/节点、复跑结果和人工复核结果。

## 9. 交接与完成

反馈改变范围、行为、终端、权限/数据范围、冲突解决或阻塞业务决策时，重新打开清单门禁。已批准范围内的纯视觉细化可以使用新的设计批次版本，不必重新建清单。

最终报告说明产物位置、批次、模块、独立 Frame、清单版本和功能 ID、终端、target、注释、状态、证据来源、冲突结果、审批、未验证项和下一 Skill。所需集成、基线、审批或验收证据不可用时，不得称产物完成。
