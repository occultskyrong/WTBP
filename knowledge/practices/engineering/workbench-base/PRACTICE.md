# 个人工作台基座选型与模块约定

## 问题定义

开发者需要一个本地优先的个人工作台，渐进聚合 AI 用量、待办和系统状态等模块。关键决策是面板形态、持久化方式与模块扩展机制。

## 适用场景

- 个人单机使用，需要聚合多个本地工具的信息。
- 模块会随需求逐步增加，新增模块不应改动基座业务逻辑。

## 不适用场景

- 多人协作、登录鉴权或远程运维面板。
- 需要第三方插件分发或运行时热加载的平台。

## 决策变量

- 面板形态：CLI 报告、桌面应用或本地 Web 服务。
- 持久化：文件系统、SQLite 或服务型数据库。
- 模块发现：显式注册、动态扫描或配置驱动。

## 候选方案

- 本地 Web 服务：开发成本低，适合中等频率的模块扩展。
- 桌面应用：原生体验较好，但基座成本更高。
- CLI 报告：极简，但不适合可视化趋势与交互聚合。

## 场景化推荐规则

单人单机且扩展频率中等时，优先本地 Web 与 SQLite；模块频繁增加时，优先显式注册以获得编译期可见性；出现多用户或远程访问需求时，重新评估鉴权和存储边界。

## 反模式

- 为单屏聚合场景预先引入多页路由和复杂插件系统。
- 用动态文件扫描发现模块，直到运行时才暴露错误。
- 在基座层写入模块的业务数据逻辑。

## 验证方法

1. 确认开发环境可一键启动，并且服务只监听预期本地地址。
2. 按模块契约新增一个空模块，验证仅增加注册项即可出现可识别的卡片。
3. 检查基座、模块数据边界和展示层之间没有反向依赖。
