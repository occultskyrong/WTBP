# WTBP Skill 框架

这是 WTBP 中所有 Skill 的统一上位框架。Skill 是一个登记了输入、副作用、输出、证据和生命周期状态的、
有边界且可重复的能力，不是提示词片段；模型生成了看似合理的文字，也不代表 Skill 已经完成。

## 五层架构

各层有先后关系。后层不能无声地替前层补造缺失决策。

1. **意图与范围**——记录目标、场景、约束、非目标、所需证据，以及最终接受的决策或产物。
2. **能力与路由**——`knowledge/skill-index.yaml` 是能力卡的唯一来源，`knowledge/skill-routes.yaml` 只负责任务匹配。
   当前会话负责做语义上的 `select`、`clarify` 或 `no_match` 判断；关键词匹配不能执行或安装 Skill。
3. **受边界约束的执行**——加载最小的目标 Skill，先检查输入契约，再执行工作流，只申请能力卡声明的副作用。
   缺少必需输入、权限或外部依赖时必须停止。
4. **证据与验收**——按输出契约产出结果，尽可能附上确定性证据，分开模型判断和人工判断，并执行完成门禁。
   dry-run、截图或生成报告只能证明对应检查，不等于未执行的运行时、视觉或外部模型验收已经通过。
5. **治理与生命周期**——保持 Skill、中文对照、目录、索引、路由、Eval 以及 `validated_by` 关系同步。
   在证据和门禁达到要求前保持 `candidate`；需要记录版本、核验日期、废弃原因和替代项。

## Skill 最小契约

每个 `skills/<skill-id>/SKILL.md` 必须包含以下契约章节。执行特有的证据门禁可以放在工作流阶段之间，但不能替代这些契约，
也不能让完成条件变得隐含：

1. `Input Contract`——必需输入、假设、可选输入，以及阻断安全推进的最小澄清问题。
2. `Workflow`——从接收任务到交付的有序步骤，每步写明证据或决策边界。
3. `Boundaries` 或等价的明确章节——非目标、副作用限制和失败即停止条件。
4. `Output Contract`——稳定字段、产物路径或 ID、未解决项和语言规则。
5. `Completion Gate`——确定性检查、必需的人工或外部检查，以及明确的停止条件。

frontmatter 中的 `name` 必须与目录名一致。英文文件是 AI 规范源，并必须有同目录的 `<name>.zh-CN.md`，规则保持一致。
参考资料按需渐进加载，不得一次性把整个目录灌入上下文。

## 登记与证据关系图

本地 Skill 的最小关系图为：

```text
SKILL.md
  ├─ 能力卡  -> knowledge/skill-index.yaml
  ├─ 路由    -> knowledge/skill-routes.yaml
  ├─ 目录对象 -> knowledge/catalog.yaml
  ├─ 评测    -> knowledge/evals/<skill-id>/EVAL.md + cases.yaml
  └─ 验证关系 -> knowledge/relationships.yaml（validated_by）
```

所有关系必须指向同一个 `skill-id`。缺失关系、过期核验日期或互相矛盾的状态都是登记失败，不能靠猜测绕过。
目录只描述可发现对象，不能覆盖能力索引、路由或 Skill 契约。

## 门禁模型

| 门禁 | 要回答的问题 | 失败时的封闭动作 |
|---|---|---|
| G0 登记 | 路径、ID、目录、路由、中文对照、Eval 和关系是否一致？ | 不路由、不提交该 Skill。 |
| G1 接收 | 目标、范围、约束、输入和验收证据是否完整？ | 只询问最小缺失澄清。 |
| G2 边界 | 非目标、副作用、权限、外部依赖和安装授权是否明确？ | 不执行、不安装、不扩展范围。 |
| G3 执行 | 有序工作流是否真正执行并保留中间证据？ | 报告首个失败步骤，不能声称完成。 |
| G4 输出 | 结果是否符合输出契约并列出未解决项？ | 标记未完成，返回修正。 |
| G5 评测 | Eval 是否覆盖正向、反向、边界及必要对抗用例，并达到门槛？ | 保持 `candidate` 或 `improve`，不能凭直觉批准。 |
| G6 生命周期 | 版本、状态、核验日期、废弃/替代关系和变更级别是否一致？ | 修正元数据和版本后再交付。 |

## 生命周期与渐进披露

默认生命周期是 `discover -> analyze -> design/evolve/implement -> verify -> evaluate -> maintain`。
发现阶段加载能力卡和路由；执行阶段只加载一个 Skill；只有当前步骤需要时才加载参考资料和 Eval。
新增 Skill 必须对应稳定、重复的任务，拥有独立边界，并具备最小 Eval 矩阵；否则应复用已有 Skill 或登记固定版本的外部 Skill。

`active` 可直接选择，`candidate` 只能在当前会话确认范围后选择，`stale` 不作为默认推荐，`deprecated` 只能用于迁移或审计。
外部 Skill 必须固定版本、在许可范围内、声明权限，并在明确授权后安装。

## 审查清单

宣布 Skill 变更完成前，确认：

- 五层架构和六道门禁都有责任人和证据；
- 英文 Skill、中文对照、索引、路由、目录、Eval 和关系一致；
- 没有把关键词匹配当成语义执行，也没有把 dry-run 当成运行时证明；
- 副作用和安装权限不超过能力卡登记范围；
- 下一步交接、未解决风险和验证命令明确。
