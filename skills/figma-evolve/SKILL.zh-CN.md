# 演进 Figma 设计

在不重新从 PRD 开始、也不悄悄破坏既有工作的前提下修改当前 Figma 设计证据。Figma 节点是当前设计来源；用户提供的 PRD 变更仍是业务来源。

开始前读取 [`../../knowledge/design-workflow.md`](../../knowledge/design-workflow.md)。它定义共享的证据优先级、清单审批、批次/Frame 组织、注释、文案分类和渲染验收契约。

## 必需输入

- Figma 文件或明确节点链接。
- 变更请求；可选相关 PRD 差异。
- 模式：默认 `patch`，只有用户明确要求有范围的重做时才用 `regenerate`。
- 已批准的清单，或足以重建 `INV-YYYYMMDD-VNN` 的信息；重叠设计还需要源设计时间和权威基线。

未给出范围节点时，先检查文件，并询问能安全修改的最小范围。不得自行选择权威版本或编造业务规则的解决方案。

## 工作流

1. 用只读身份/权限证明预检可调用的 Figma 集成；修改前读取目标节点、父级上下文、组件、变量、约束、标注和当前截图。
2. 重述预期变更，创建或确认 `INV-YYYYMMDD-VNN`，包含稳定功能 ID、状态、证据定位、受影响页面/状态/targets 和冲突决策。除非已有批准清单明确覆盖，否则修改前必须审批。
3. 分配 `YYYY-MM-DD-VNN` 设计批次。请求或当前证据产生实质冲突时停止，提供不同解决方案并重新打开清单门禁。
4. `patch` 模式只修改目标节点及必要的共享组件，保留有效的 Auto Layout、约束、Variants 和资源链接。
5. `regenerate` 模式创建如 `V2` 的新版页面或 Frame，保留原页面/Frame 并返回两者链接。默认不得替换整个文件。
6. 确保每个受影响功能都在完整容器页面中，并有右侧独立注释块。分类 Frame 内文案，记录来源、建议文案、操作、状态和例外。
7. 重新读取已修改节点，检查注释几何，截图并记录验收结果，指出哪些下游 target 需要再次执行 `figma-to-product` 或 `figma-verify`。

## 变更规则

- 不得只为贴近截图，就把普通内容改成 absolute 定位的子元素。
- 只有请求范围确实包含其消费者时才改共享 Tokens 或组件；必须报告这些消费者。
- 变更说明放在产品 UI 外。
- 本 Skill 不实现 Web、小程序或 App 代码。
- 不得凭节点修改成功或单张截图称视觉变更完成，必须完成共享的几何、文案、状态、可访问性和渲染验收审计。

## 问题驱动的变更场景

| ID | 给定条件 | 必须动作 | 通过条件 |
|---|---|---|---|
| E-01 | 请求只调整一个 Frame 的局部间距。 | 使用 `patch`；先检查其父级 Auto Layout 和共享 Token 消费者。 | 只有范围内节点变化，且已列出受影响 targets。 |
| E-02 | 重做会改变组件层级或布局行为。 | 使用 `regenerate`，创建 `V2`，而非覆盖基线。 | 新旧版本链接都存在，并明确下游实现影响。 |
| E-03 | 请求的视觉修复会把普通子元素改为 absolute。 | 在浮层意图和包含父级有证据前拒绝该修改。 | 不引入只依赖坐标的规避方案。 |

## 输出契约

返回：

```text
Figma 来源与所选模式
请求变更和业务规则冲突
清单版本、功能 ID、审批和设计批次
变更前后节点链接
已变更页面/组件/状态及受影响 targets
已检查截图
注释 ID、文案分类、几何和验收记录
重生成时保留的版本链接
未验证项和所需下一 Skill
```
