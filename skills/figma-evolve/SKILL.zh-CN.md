# 演进 Figma 设计

在不重新从 PRD 开始、也不悄悄破坏既有工作的前提下修改当前 Figma 设计证据。Figma 节点是当前设计来源；用户提供的 PRD 变更仍是业务来源。

开始前先读取 [`../../knowledge/design-principles.zh-CN.md`](../../knowledge/design-principles.zh-CN.md)，再读取 [`../../knowledge/design-workflow.zh-CN.md`](../../knowledge/design-workflow.zh-CN.md)。两者共同定义分层设计契约、证据优先级、清单审批、批次/Frame 组织、注释、文案分类和渲染验收契约。

## 输入契约

- Figma 文件或明确节点链接。
- 变更请求；可选相关 PRD 差异。
- 模式：默认 `patch`，只有用户明确要求有范围的重做时才用 `regenerate`。
- 已批准的清单，或足以重建 `INV-YYYYMMDD-VNN` 的信息；重叠设计还需要源设计时间和权威基线。
- 设计变更所服务的消费项目仓库/工作树和预览入口；如果是 Figma-only 变更，必须明确记录没有实现项目纳入范围。
- 终端外框契约：终端、准确视口/设备尺寸、安全区和导航/状态面。`miniapp` 必须明确小程序外框，不得凭空添加通用设备框。
- 当前 `ICON-YYYYMMDD-VNN` 清单，或足以确认受影响 Icon 映射和资产家族是否仍有效的项目证据。

未给出范围节点时，先检查文件，并询问能安全修改的最小范围。不得自行选择权威版本或编造业务规则的解决方案。

## 工作流

1. 用只读身份/权限证明预检可调用的 Figma 集成；修改前读取目标节点、父级上下文、组件、变量、约束、标注和当前截图。
2. 重述预期变更并检查消费项目，创建或刷新 `PDC-YYYYMMDD-VNN`，通过 `PDC-01`–`PDC-06`：项目身份、表面、设计基础、行为/约束、复用/变更边界及证据。Figma-only 工作要明确记录实现边界和 `Unverified` 字段。
3. 解决项目契约冲突。结构变更或 `regenerate` 时，必须先基于已批准 PDC 推导或刷新 `ARC-YYYYMMDD-VNN`，再创建或刷新并获得 `INV-YYYYMMDD-VNN` 审批，最后才建立或刷新 `ICON-YYYYMMDD-VNN` 并通过 `IA-01`–`IA-07`；范围很小的 patch 只有在契约不变时才能复用当前架构，且只有批准范围以及受影响 Icon 的语义映射/资产家族均不变时才能复用 Icon 清单。记录模块、路由、外框、复用边界、状态/转移、受影响的底层窗体批次和 Icon 影响。除非已有批准清单明确覆盖，否则修改前必须审批。
4. 分配 `YYYY-MM-DD-VNN` 设计批次。请求或当前证据产生实质冲突时停止，提供不同解决方案并重新打开清单门禁。
5. `patch` 模式只修改目标节点及必要的共享组件，必要时包含已批准的 Icon 组件；保留有效的 Auto Layout、约束、Variants 和资源链接。
6. `regenerate` 模式创建如 `V2` 的新版页面或 Frame，保留原页面/Frame 并返回两者链接。默认不得替换整个文件。
7. 确保每个受影响功能都在完整容器页面和声明的终端外框中，并有右侧独立注释块。新增页面/状态或结构重设计时，先用中性占位为所有批准页面/状态构造或重新验证底层窗体批次。产品 Frame 不得写入设计/项目/技术说明；分类 Frame 内文案，记录来源、建议文案、操作、状态和例外。
8. 在新增或修改页面级样式前，执行并记录阻断检查点（`BF-01`–`BF-06`）。只有结构契约未变化且已有批准底线时，局部 patch 才可复用原底层窗体；否则必须覆盖完整受影响批次。
9. 重新读取已修改节点，对所有产品页面/状态 Frame 执行共享写入后结构门禁（`G-01`–`G-06`），检查外框和注释几何，获取完整外框截图并记录验收结果，指出哪些下游 target 需要再次执行 `figma-to-product` 或 `figma-verify`。

## 变更规则

- 不得只为贴近截图，就把普通内容改成 absolute 定位的子元素。
- 只有请求范围确实包含其消费者时才改共享 Tokens 或组件；必须报告这些消费者。
- 变更说明放在产品 UI 外。
- 本 Skill 不实现 Web、小程序或 App 代码。
- 不得凭节点修改成功或单张截图称视觉变更完成，必须完成共享的几何、文案、状态、可访问性和渲染验收审计。
- 新增或结构变化的页面在所有底层 Frame 通过 BF-01 至 BF-06 前，不得叠加页面级样式；底层批次不完整时必须阻断变更。
- 消费项目契约未通过 PDC-01 至 PDC-06 或未明确 Figma-only 边界时，不得自行选择新模块、页面族、组件基础或视觉方向。
- 不得把页面局部 Vector、emoji、文字图标、截图裁切或未经批准的第三方集合当作可复用 Icon。必须复用已批准的语义 Icon 家族；缺失 Icon 必须在放入页面前独立设计。
- 任一页面没有记录 `layoutMode`/布局责任层、一一对应注释、文字容器边界结果或实例/Master 尺寸比例时，不得完成写入；已审批例外必须写明受影响 Frame 和原因。
- 终端外框/尺寸缺失、完整外框未出现在截图中，或产品 Frame 出现描述性/技术/评审文字时，写入必须阻断。这些是 G-05/G-06 失败，必须有明确审批例外。

## 问题驱动的变更场景

| ID | 给定条件 | 必须动作 | 通过条件 |
|---|---|---|---|
| E-01 | 请求只调整一个 Frame 的局部间距。 | 使用 `patch`；先检查其父级 Auto Layout 和共享 Token 消费者。 | 只有范围内节点变化，且已列出受影响 targets。 |
| E-02 | 重做会改变组件层级或布局行为。 | 使用 `regenerate`，创建 `V2`，而非覆盖基线。 | 新旧版本链接都存在，并明确下游实现影响。 |
| E-03 | 请求的视觉修复会把普通子元素改为 absolute。 | 在浮层意图和包含父级有证据前拒绝该修改。 | 不引入只依赖坐标的规避方案。 |
| E-04 | 变更涉及等权导航或嵌套组件边界。 | 在添加样式前，对受影响底层批次重新验证分布和父子链几何。 | 不存在手工摆放导航或无法解释的子节点溢出。 |

## 输出契约

返回：

```text
Figma 来源与所选模式
请求变更和业务规则冲突
项目设计契约修订号、PDC-01 至 PDC-06 结果、推导出的架构修订号（`ARC-YYYYMMDD-VNN`）和证据边界
结构或 Icon 变化时的 Icon 资产清单修订号、受影响语义映射和 `IA-01`–`IA-07` 结果
清单版本、功能 ID、审批和设计批次
变更前后节点链接
已变更页面/组件/状态及受影响 targets
结构变化时的底层 Frame ID 和 BF-01 至 BF-06 检查点结果
已检查截图
注释 ID、文案分类、几何和验收记录
终端外框契约和尺寸
所有产品页面/状态 Frame 的 `G-01`–`G-06` 写入后门禁结果
页面/状态/转移矩阵和变更的交互决策
重生成时保留的版本链接
未验证项和所需下一 Skill
```

## 完成门禁

- 已记录输入范围、清单审批、设计批次和冲突决策。
- 已检查消费项目并通过 PDC-01 至 PDC-06，或已明确 Figma-only 边界和 `Unverified` 字段。
- 结构变更已基于批准的项目设计契约记录 `ARC-YYYYMMDD-VNN`，且没有未记录的路由、页面族、设计基础、终端、状态或行为。
- 结构或 Icon 相关变更已有当前 `ICON-YYYYMMDD-VNN`；页面级样式前 `IA-01` 至 `IA-07` 已通过，或已记录复用的映射/资产家族确实未变化。
- 每个受影响及未变更的产品页面/状态 Frame 都有 G-01 至 G-06 结果，或有明确批准的例外；每个新增/结构变化的底层批次都先通过 BF-01 至 BF-06。
- 已提供完整外框的前后链接、截图、交互矩阵和下游交接；否则必须标记为未完成。
